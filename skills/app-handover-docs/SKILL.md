# 应用交接文档生成器

为一个已经拿到源码的企业级应用，产出新人可直接接手的四分册 Word 文档。

## 核心原则

本技能产出的是**工程交接资料**，不是营销文案。最高准则是**事实可追溯、不存在臆测**：
源码和材料中能证实的写进正文并标注出处；能推断的标注"（推断）"；
无法确定的登记到《待确认清单》，绝不填充业界通用做法伪装成本项目的实际情况。

完整红线规则见 `references/writing-rules.md` ——**撰写前必须加载该文件**。

---

## 工作流

### 阶段 0 · 信息采集

在动手前确认以下四项。**缺失时主动询问用户，不要猜测**（猜测的路径会让后续全部返工）：

1. **源码根目录**（绝对路径）
2. **交接材料**（文档路径，或明确告知没有）
3. **应用的对外正式名称**（用于封面，如"订单中心"、"XX 营销平台"）
4. **输出目录**（Word 文件存放位置），以及**本次要生成哪几册**（默认四册全出）

对于信息混乱的批量场景，用 `assets/handover-intake.md` 作为统一的信息采集清单，
让用户按项填写或回答。**有多个应用要接手时，逐个应用独立执行本流程，不要混在一起。**

### 阶段 1 · 源码静态扫描

运行扫描脚本，产出系统事实快照：

```bash
python <skill_dir>/scripts/scan_repo.py <源码根目录> [-o <输出目录>] [--no-git]
```

脚本为**纯标准库、零依赖**，Windows / macOS / Linux 均可直接用系统 Python 运行。
默认在源码目录下生成 `_handover_scan/`（建议提醒用户将其加入 `.gitignore`）。

生成 9 个文件，用途如下：

| 文件 | 用途 |
|---|---|
| `00_SUMMARY.md` | **先读这个**，系统画像速览 + Git 协作线索 + 风险提示 |
| `01_structure.md` | 模块结构、启动入口、大文件 |
| `02_dependencies.md` | 依赖清单与中间件推断 |
| `03_endpoints.md` | HTTP 接口全集、Feign 下游依赖 |
| `04_data.md` | 数据实体、Mapper、DDL、数据源地址 |
| `05_jobs_and_mq.md` | 定时任务、消息队列收发点 |
| `06_config.md` | 配置项（**敏感键值已自动脱敏**） |
| `07_deploy.md` | Docker / Compose / K8s / CI / Nginx |
| `08_quality.md` | TODO、全局异常处理、热点改动文件 |
| `scan_data.json` | 全量结构化数据，接口数超过 500 时读这个补全 |

**注意**：扫描结果是**线索清单而非结论**。写入文档的关键条目（接口路径、定时表达式、
表名、配置项含义）必须打开源码核实一次，不可直接照抄。已知局限见 `references/writing-rules.md` 第三节。

### 阶段 2 · 材料整合与关键源码深读

1. 读取用户提供的交接材料。`.docx` / `.pdf` 需用相应工具先转换为可读文本。
2. 用扫描报告**校验**交接材料：材料与代码冲突时，以代码为准并在正文注明差异。
3. **深读源码补充静态扫不到的部分**（决定文档质量高低的关键一步，不可跳过）：
   - 枚举类 / 常量类（`*Enum`、`*Status`、`*Type`、`*Constant`）→ 还原业务状态码字典
   - 校验与异常抛出点 → 还原业务规则
   - 状态变更调用点（`setStatus` / `updateStatus`）→ 拼出单据状态机
   - AOP 切面、拦截器、过滤器、MyBatis 拦截器 → 横切逻辑（鉴权、幂等、限流）
   - 一个核心业务流程的完整调用链 → 用于技术手册的"代码地图"

   代码量大时，用 Explore 子代理并行深读，明确要求它返回文件路径 + 行号 + 事实。

4. 建立两张内部清单并贯穿后续写作：
   - **事实清单**：每条含结论 + 出处（文件路径:行号）+ 可信度等级（A/B）
   - **待确认清单**：所有源码与材料都无法确定的事项

### 阶段 3 · 分册撰写

加载 `references/doc-outlines.md`，按其章节结构撰写。**必须同时遵守 `references/writing-rules.md`。**

产出四册 Markdown（`01_business.md` / `02_tech.md` / `03_ops.md` / `04_onboarding.md`），
置于输出目录的 `md/` 子目录。四册分工：

- **业务手册**：定位、术语表、核心业务流程、功能清单、业务规则与状态机、数据字典
- **技术手册**：技术选型、部署架构、开发架构、技术架构、数据架构、接口、
  异步消息、定时任务、配置、异常日志、安全、技术债
- **运维手册**：资源台账、发布 SOP、告警处置对照表、故障 Runbook、
  定时任务运维、数据运维、日志路径、应急预案、巡检清单
- **接手速查手册**：一页纸速览、环境申请清单、本地搭建 Step by Step、
  必读代码地图、关键联系人、学习路径、**待确认清单**

去重原则：业务流程只在业务手册完整讲；部署拓扑在运维手册详画、技术手册引用。
交叉一律写"详见《XX手册》第 X 章"。

**《待确认清单》不应为空**——一个真实的企业系统必然存在扫不出来的信息。
若它为空，说明编写时臆造了内容。

### 阶段 4 · Word 排版与交付

1. 逐册加载 `workbuddy-docx` 技能，将 Markdown 转换为排版规范的 `.docx`。
   必须告知该技能：需要**封面 + 自动目录 + 页眉页脚页码 + 表头加粗全边框表格 + 版本记录表**。
2. 文件命名：`<应用名>-业务手册.docx`、`-技术手册.docx`、`-运维手册.docx`、`-接手速查手册.docx`。
3. 交付时用 `present_files` 展示四份 Word，并在回复中说明：
   - 本应用的技术栈与规模一句话概括
   - **遗留的《待确认清单》条目数**（以及最需要优先确认的 3 条）
   - 文档中标注了"（推断）"的关键结论

## 质量门槛（交付前逐项核对）

- [ ] 所有关键事实都带源码出处，或明确标注"（推断）"
- [ ] **全文没有任何生产 IP / 口令 / 密钥 / 证书私钥**
- [ ] 告警阈值、联系人电话、业务量级等**未见写明则不编造**，已在清单中登记
- [ ] 接口路径、定时表达式、表名与源码逐条核对过，不是照抄扫描报告
- [ ] 五张核心图齐备：系统上下文图、核心流程图、状态机图、部署架构图、技术架构图
- [ ] 运维手册每条命令可执行且带预期输出
- [ ] 每册有封面、目录、页码、版本记录表
- [ ] 四册之间无整段重复

## 常见场景应对

- **交接材料很全**：仍要跑扫描脚本做交叉校验，材料中往往有过时的描述（尤其是配置与接口）
- **完全没有任何交接材料**：靠源码反推，此时《待确认清单》会显著变长，属于正常现象
- **单体巨石应用**：优先深读模块边界与共享表，文档里明确标注"哪些模块是历史遗留、不推荐修改"
- **多个微服务**：每个服务独立成文档；另可额外产出一份《服务间调用关系总览》
- **用户只需要某一册**：按 `doc-outlines.md` 中对应册的大纲执行即可，无需生成全部四册
