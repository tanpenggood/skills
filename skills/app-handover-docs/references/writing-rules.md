# 写作规范、事实可信度与防编造红线

交接文档是用于**真实接手生产系统**的工程资料。一份看起来完整但掺了臆测内容的文档，
比一份坦率标注"此处未确认"的文档危害更大——新人会照着错误的信息执行操作。
以下规则为强制约束。

---

## 一、事实可信度三级标记

编写过程中，对每一条将要写入文档的结论，先判定它的来源等级：

| 等级 | 标记方式 | 含义 | 典型来源 |
|---|---|---|---|
| **A 级 · 代码实证** | 正常叙述，**带出处** | 代码里客观存在，可验证 | `OrderController.java:45` 定义了 `POST /api/order/create` |
| **B 级 · 材料推断** | 标注"（据交接材料）"或"（推断）" | 有依据但非直接证据，或由多处线索合理推导 | 由 MySQL + MyBatis 依赖推断使用了关系库；由 pom 推断技术栈 |
| **C 级 · 缺失未知** | **不写入正文**，登记到《待确认清单》 | 源码和材料都无法确定 | 生产实际 IP、业务规则的业务含义、告警阈值 |

### 硬性宣布规则

- **C 级内容禁止出现在正文叙述中**，必须进入速查手册第 9 章《待确认清单》。
- **B 级内容必须带上来源标注**，让读者知道这是推断而非实证。
- 即使 A 级内容，只要是关键结论（尤其运维操作类），也应写明依据文件路径，便于后续复核。

## 二、绝对禁止编造的内容（红线清单）

以下信息**永远无法**从静态源码和文档中可靠获得，**严禁凭通用最佳实践填充**：

| 禁区 | 为什么危险 | 正确做法 |
|---|---|---|
| **生产环境 IP / 域名 / 端口** | 不同环境千差万别，编造后新人照着连会连错 | 标注「需向运维确认」，留待核实。若 config 扫描到地址，注明"（来自配置文件，需核实是否为最新）" |
| **账号、口令、密钥、证书** | 泄露风险 + 编造会被误用 | 一律写「由配置中心/密钥管理服务托管，不落文档」 |
| **告警阈值**（CPU > X% 告警等） | 纯属团队约定，代码里没有 | 留空待确认，只描述"应监控哪些指标" |
| **具体对接人姓名与电话** | 错的人会被半夜叫醒 | 只能写 Git 提交中出现的账号名，并标注"（建议核实是否仍在职）" |
| **业务量级数据**（日订单量、QPS） | 编造的容量数据会误导容量决策 | 留待确认，或写"未获取到" |
| **灾难/故障历史与事故复盘** | 属组织记忆，代码里没有 | 留待确认 |
| **未被代码证实的性能数据** | 压测数据必须是测出来的 | 留待确认 |
| **域外规则**（法律法规、政策条款、第三方平台规则） | 极易产生幻觉 | 只描述"本系统对该规则做了什么处理"这类可验证陈述 |

### 特别警惕：通用运维知识的"自动联想"

最常见的越界是把行业通用做法伪装成本项目的实际情况，例如：

- ❌ 错误："数据库连接池配置最大连接数 50，超过会拒绝请求"
  （配置里其实没有显式配置 druid maxActive，这是默认值联想）
- ✅ 正确："连接池未显式配置 maxActive，走 HikariCP 默认 10。生产实际用量需向 DBA 确认。"

判断标准：**这句话能不能给出代码/配置出处？给不出，就不能写成陈述句。**

## 三、静态扫描结果的固有局限

`scan_repo.py` 是正则启发式扫描，已知以下局限，引用其输出时必须意识到：

1. **路径可能不完整**：动态注册的路由、反射调用的处理器扫不到
2. **方法名可能误判**：注解与签名之间有多行时可能取错方法名
3. **注释缺失不代表功能不重要**：`注释列` 为空只说明没有写注释
4. **依赖推断可能过度命中**：例如依赖名含 "weixin" 不代表真的做了微信对接（可能只是传递依赖）
5. **跨继承/切面的行为扫不到**：AOP 拦截、过滤器链、拦截器、MyBatis 拦截器都不在接口清单里
6. **切面增强的幂等/鉴权/限流逻辑扫不到**：这类横切关注点需人工补充

**使用原则**：扫描报告是**线索清单**，不是结论。对写入文档的关键条目，
应当打开对应源码文件核实一次，尤其是：接口路径、定时任务表达式、表名、配置项含义。

## 四、从源码反推系统全貌的方法路径

当交接材料缺失或不可靠时，按以下顺序还原一个陌生系统：

### 第 1 步：定边界（这个系统是什么）
- 看 README、`pom.xml`/`package.json` 的 `artifactId`/`name`、`spring.application.name`
- 看 Git 远程地址，通常带了组织名和服务名

### 第 2 步：找主干（核心数据流）
- 从**启动类**入手 → 找到全局配置类 → 找到核心 Controller
- 顺着 Controller → Service → Mapper 走一条完整调用链
- **写操作优先**：只读代码看懂不了业务，从"谁在改数据"倒推业务意图
- 读 `05_jobs_and_mq.md` 的消息/任务，异步链路里常有核心逻辑

### 第 3 步：还原业务（这一步最需要人）
- 优先读**注释 Swagger/操作手册**，再读方法名，再读方法体
- 找出所有**枚举类和常量类**（`*Enum`、`*Status`、`*Type`、`*Constant`）——
  这是还原业务状态码字典的钥匙，也是业务手册第 2、5 章的素材来源
- 找出**校验逻辑**（`throws BusinessException`、`Assert`、`validate*`）——
  校验的就是业务规则
- 找出**状态流转**（`setStatus`、`updateStatus` 调用点）——拼出状态机

### 第 4 步：画外部关系
- Feign / Dubbo 客户端 = 我依赖谁
- Controller = 谁依赖我（需结合调用方核实）
- MQ Topic = 异步的上下游
- 配置里的 URL = 第三方系统对接

### 第 5 步：确认不确定性
- 源码看不懂的地方 → 登记《待确认清单》
- 找到 Git 提交最多的文件 → 说明这块是活代码
- 找到最近半年改得最多的人 → 最可能答得上问题的人（**需核实是否仍负责**）

## 五、语言与表达规范

- **用中文简体**，技术专有名词保留英文原文（如：`@Scheduled`、`pom.xml`、Spring Boot）
- 使用**陈述句**，避免"可能"、"也许"这类含混词；不确定就走 C 级处理
- 表格优先于段落：交接文档是**查阅型资料**，不是**阅读型文章**
- 每条命令都要给出**预期输出**；只给命令不给预期的用不了
- 章节之间保持信息不重复，交叉处用"详见"
- 相同含义的术语全文统一，不要一会儿"消息主题"一会儿"topic"

## 六、交付前的自检清单

四册全部写完后，逐项检查：

- [ ] 每册都有封面、目录、页码、版本记录表
- [ ] 五张核心图都画了（系统上下文、核心流程、状态机、部署架构、技术架构）
- [ ] 所有接口路径、定时表达式、表名都与源码**逐条核对过**，不是照抄扫描报告
- [ ] 全文**没有一个具体的生产 IP / 口令 / 密钥**
- [ ] B 级推断都在显著位置标注了来源或"（推断）"
- [ ] C 级内容全部进入《待确认清单》，且清单不少于 8 条
   （一个真实的企业系统，不可能什么都搞清楚）
- [ ] 运维手册的每条命令都能复制执行，且带有预期输出
- [ ] 还没有任何一处把"业界通用做法"写成了"本系统的做法"
- [ ] 文档之间无整段重复
- [ ] 每册末尾列出了所用的素材来源

**如果《待确认清单》是空的，说明这份文档很可能臆造了过多内容——这是一个危险信号。**
