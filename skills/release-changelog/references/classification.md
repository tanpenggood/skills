# 提交分类与风险判定规则

## 〇、净变更优先（net diff first）

- 事实认定以「范围基线 → 终态」的净 diff 为准；**不逐 commit 分析范围内中间演变，不把中间过程写进 CHANGELOG**。
- 范围内新建的文件按「全新代码」理解（净 diff 中即为完整终态），不要当作多次修改的叠加来描述。
- 范围内先改后回、最终相互抵消的改动不出现在净 diff 中，也不应出现在 CHANGELOG 里。
- commit 的 type message（feat/fix/...）与 hash 只用于把净变更**归组**到功能/修复/优化条目并标注溯源 hash；条目内容必须来自净 diff 事实，不逐 commit 复述。
- 下方分类表的判定依据同样适用于净 diff 视角的文件状态：新增文件/新增对外接口 → 新功能；条件判断、边界、异常处理的修改 → BUG 修复；以此类推。一个文件既含新逻辑又含缺陷修正时，按条目粒度拆开描述，各自标注溯源 commit。

## 一、改动类型判定

按下述优先级判定，commit message 只是线索，**最终以 diff 内容为准**：

| 类型 | 判定依据 | 归入章节 |
| --- | --- | --- |
| 新功能 (Feature) | 新增文件/新增对外接口/新增配置项且带业务逻辑；message 含 feat、新增、支持、实现 | ✨ 新增功能 |
| BUG 修复 (Bugfix) | 修改条件判断、边界处理、异常捕获、空指针/并发/数据一致性修复；message 含 fix、修复、bug、hotfix | 🐛 问题修复 |
| 性能优化 (Performance) | 缓存引入、SQL/查询优化、批量化、异步化、算法替换、连接池/线程池参数调整；message 含 perf、优化、性能、提速 | ⚡ 性能优化 |
| 重构 (Refactor) | 结构变动但外部行为不变：改名、抽方法、分层调整、删除死代码 | ♻️ 重构与调整（归入"其他变更"） |
| 依赖升级 | package.json / go.mod / pom.xml 等 lock 文件与依赖声明变化 | 📦 依赖变更 |
| 配置变更 | .env、application.yml、CI 配置、Dockerfile、编排文件 | ⚙️ 配置与基础设施 |
| 文档 | 仅 .md / docs / 注释 | 📝 文档 |
| 测试 | 仅 test / spec / e2e | 🧪 测试 |
| 样式/文案 | 纯 UI 调整、文案替换 | 💄 界面与文案 |

规则：
- 一个 commit 同时命中多类时，按「新功能 > BUG 修复 > 性能优化 > 依赖 > 配置 > 重构 > 其他」取最高优先级，其余在描述里体现。
- 只改测试或文档的 commit，**不要**写进"新增功能/修复/优化"章节，单独归入对应小节。
- merge commit 默认忽略；若用户要求包含，只统计其引入的实质改动。
- 无法从 message 与 diff 判断意图时，归入"其他变更"，并在「待确认事项」列出，不要臆测成新功能。

## 二、影响面分析

1. 用报告里的 `modules` 字段做模块聚合，输出「模块 → 改动量(增删行) → 涉及 commit 数 → 主要变更文件」。
2. 判断跨模块影响：一次改动触及 3 个以上模块，或改动了公共组件/基础库/公共协议文件，需在文中显式标注「跨模块影响」。
3. 判断对外可见性：改了接口契约（proto/openapi/controller/route）、DB 表结构、配置项默认值、消息/事件格式 → 视为对外可见变更，必须在「兼容性提示」中写明调用方需要做什么。新增对外 API 接口时，还必须在「发版检查项」中列出该接口的完整路径，提醒在云平台网关上完成配置、发布并授权给相应应用。
4. 判断是否需要数据迁移：出现 migrations/*.sql、ALTER TABLE、字段新增/重命名、历史数据回填脚本 → 必须在「发版检查项」里写明执行顺序（先迁库还是先发版）。

## 三、风险项判定（脚本已预标注，需人工复核）

脚本输出的 `risk_items` 按以下类别预标注，写作时需逐个核实并给出结论，不能原样罗列：

- **数据库变更/迁移**：是否可回滚、是否锁表、大表 DDL 耗时。
- **脚本执行**：本次发版是否需要额外人工执行脚本（数据修复、初始化、清理）。必须明确写出脚本路径、作用、执行时机、执行账号。
- **CI/CD 流水线**：流水线改动可能影响构建/发布流程本身，需提示发版前先验证流水线。
- **配置/环境变量**：新增配置项是否已在生产环境配置齐全；缺失时的默认行为是否安全（尤其开关类配置）。
- **依赖升级**：主版本升级是否含不兼容变更；安全补丁类升级需说明修复的 CVE/漏洞影响面。
- **接口契约/协议**：字段增删、枚举变更、必填性变化，是否与调用方兼容。
- **网关接口配置**：新增对外 API 接口（Controller 中新增 `@RequestMapping`/`@GetMapping`/`@PostMapping` 等方法，或 proto/openapi 中新增路由）时，需确认该接口已在云平台网关完成配置、发布并授权给相应应用。未配置网关的新接口，下游应用调用会返回 404。在「发版检查项」中列出每个新增接口的完整路径，提醒运维完成网关配置。
- **鉴权/安全**：权限校验、密钥、加密逻辑改动 → 最高优先级复核项。
- **大规模删除**：单文件删除 ≥200 行，确认不是误删。
- **二进制文件变更**：无法 diff，需人工确认来源。

另外需人工补充脚本无法识别的风险：
- 删除了对外接口或字段（从 diff 里看 `public`/`export`/路由注册被移除）。
- 默认值变更导致行为变化（配置默认值、参数默认值）。
- 定时任务/消息消费者逻辑变更。
- 缓存 key 或缓存失效策略变更（可能导致缓存雪崩/脏读）。

## 四、Breaking Change

命中以下任一即需在文档顶部置顶提示：
- commit message 含 `BREAKING CHANGE`、`type!:`、`breaking:`、中文"不兼容/破坏性"。
- diff 中删除/重命名了对外接口、数据库字段、配置项。
- 接口必填参数新增、返回结构变化、错误码语义变化。
